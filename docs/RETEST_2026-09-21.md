# The smallest Claude Desktop retest for the 2026-09-21 repairs

Two of the five questions, unchanged, in the same mailbox, with the two things that
compromised the first runs turned off. Nothing here is a benchmark or a comparison, and a
result from it belongs in no material. It exists to establish four things the offline suite
cannot - that the repairs hold on the shipped process, on the real transport, driven by the
real client - and then to review the two answers against the tool results the client
actually received, which the first runs never preserved.

Corrected the same day, after the second repair: the timing check no longer accepts a
`budget_exhausted` decline on its code; every call is measured against the allowance it
bound, with a stated tolerance; the diagnostic file names nothing the server does not
publish; and the answer review is written down as a procedure with three verdicts.

## Setup, once

1. **Memory off.** In Claude Desktop, disable memory for the duration. Four of the five
   first runs read memory; whether anything carried between them is unknown, and this run
   should not inherit that question.
2. **Only Orivra connected.** Every other connector off, so the mailbox is reachable by one
   route.
3. **Diagnostics on.** Claude Desktop does not hand the server your shell's environment; the
   variable has to be in the server's own entry in `claude_desktop_config.json`. The first
   retest ran with it unset and the banner read `off`. The whole addition is one `env` block
   inside the existing `"orivra"` entry (add the key to the block if one is already there):

   ```json
   "orivra": {
     "command": "/absolute/path/to/uv",
     "args": ["run", "--directory", "/absolute/path/to/mailweave", "orivra", "serve",
              "--client", "/absolute/path/to/mailweave/mailweave-server-oauth.json"],
     "env": {
       "MAILWEAVE_DIAGNOSTICS": "/Users/<you>/mailweave-pilot/calls.jsonl"
     }
   }
   ```

   An absolute path, outside the repository. Quit Desktop fully and reopen it - the server
   is spawned at app start. Then, before the first question, read the banner in
   `~/Library/Logs/Claude/mcp-server-orivra.log`: it must say `diagnostics:     on, <that
   path>`. If it says `off (set MAILWEAVE_DIAGNOSTICS to a file path)`, the variable did not
   reach the process and nothing in part one is measurable; stop and fix the config.
4. **Fresh server.** Quit and reopen Desktop before the first question, and note that you did,
   so the structure cache is cold for question one and the first semantic query pays the
   model load (the end line records it as `cold_load_ms`, and the check sets it aside).
5. **A private folder for the raw results**, beside `calls.jsonl`. Every tool result block
   the client shows - expand each one, copy it whole - goes into a file per call, in order.
   The transcript's prose is not evidence; the tool results are.

## Part one: what the mechanisms must establish

| # | Claim | Evidence that settles it | Where it comes from |
|---|---|---|---|
| 1 | No call ran past its allowance, whatever its outcome | `python tools/dev/check_calls.py calls.jsonl --tolerance-ms 750` exits 0: every end line's `overrun_ms` (net of `cold_load_ms`, when present) is at most the tolerance - a `budget_exhausted` decline included | the diagnostics file, read by the checker |
| 2 | Every call the server received also ended | the same run reports no call "started, never ended" | the diagnostics file |
| 3 | A refusal says what to do | any `declined` line carries `recovery` and `terminal`, and the refusal text in the transcript shows `recovery:` | diagnostics file and transcript |
| 4 | Rows carry attribution and chronology with provenance | in the raw tool results, every message row has `attribution.provenance` and `internal_date_provenance`; for the rows the answer cites, `attribution.address` is set and `internal_date` is non-null | the raw tool results |

Record the checker's whole output with the run. A `LATE` line is a finding, not a note: it
names the call, its tool, its elapsed and its allowance, and it fails the claim whatever the
call's outcome was.

Every end line now also says where the call's wall clock went at the socket - `sockets`
opened, `connect_ms` (which includes name resolution), `tls_ms`, `write_ms`, `read_ms`
(waiting for Gmail's bytes) - so a late or a spent call is attributable from the file alone.
Read them on every `budget_exhausted` line and on the slowest served line: a large
`connect_ms` against a small `read_ms` is the resolver or the network path, not Gmail; a
large `read_ms` over few sockets is Gmail answering slowly; many `sockets` in one call is a
connection that keeps being closed and reopened.

### The tolerance, and where 750 ms comes from

The allowance an end line carries is the sum of the deadlines the call's Gmail requests ran
under: `MAX_SERVER_MS` (7,700) for a read, `MAX_SERVER_MS + MAX_SEMANTIC_MS` (13,700) for a
search, and for an `orivra_ask` the sum of the retrievals it ran. The deadline is enforced at
the socket: every read, write, connect and handshake is clamped to what is left of it, so the
last operation that could run over is cut at the allowance to within a socket timeout's
granularity, which is milliseconds. What runs after that clamp, or after the last network
operation of a served call, is raising and rendering the refusal, or assembling, measuring and
rendering the response, then writing the end line. Measured through the shipped tool boundary
over an instant transport on the heaviest offline fixtures - the near-cap Harbor search, a
twelve-message `body_full` read, an `orivra_ask` at the host cap - the largest of those was
33 ms, on a loaded shared runner slower than the owner's machine; and on the same runner the
real `httpx`/`httpcore` stack over a scripted socket, cut by the clamp at a 400 ms allowance
against bodies trickling at 24 bytes / 40 ms and 8 bytes / 25 ms, ended at 402-404 ms - an
overrun of 1-4 ms, and 1-2 ms on the end lines. The tolerance is the larger of those figures
with more than an order of magnitude of headroom, and still two orders of magnitude
under the failures it must catch: the four-minute read, or a body that trickles for seconds
past a sub-second allowance. Two things it deliberately does not cover, because they are not
overruns: the model load a first semantic query pays (`cold_load_ms`, set aside by the
checker, PF-4's rule) and the semantic work itself (inside the search allowance). A served
`orivra_ask` that composes several retrievals is measured against their summed allowances,
which is the honest bound and not a tight one.

If the checker reports a `LATE` line under 2 s on a search, look at the line's `cold_load_ms`
first and at whether the machine was under load second; either way record it as a finding
with the figures, and do not raise the tolerance to make it pass.

## Part two: does the answer hold against what the tools returned

For each question, with the raw tool results open beside the answer. Each row is a yes, a
no, or "not in the results".

**Question 2 - the decision.**

| Check | How |
|---|---|
| Every cited message id is in a tool result | search the raw results for the id; a citation to an id no tool returned is a fabricated citation, whatever the id turns out to be in the mailbox |
| The stated decision is in a cited message | find the sentence in the cited row's `content.text`; a decision the answer states and no cited row says is inference, and the answer must have marked it so |
| Each stated reason is in a cited message | the same, per reason |
| Each "explicitly rejected" alternative is rejected in a cited message, explicitly | "rejected" means a message says it was considered and turned down; an alternative merely absent from the chosen path is not an explicit rejection |
| The messages span the decision's reasoning | the cited rows come from more than one message, and the reasoning the answer reconstructs is distributed across them the way the answer says |
| "Insufficient evidence" was said where it was true | any claim the checks above marked "not in the results" was flagged by the answer as inference or insufficient |

**Question 4 - the two threads.**

| Check | How |
|---|---|
| Two distinct threads, both non-Harbor | two `thread_id`s in the cited rows; neither thread's subject or body is about Harbor |
| The connection is stated in the messages, not inferred from co-occurrence | a cited row in one thread refers to the project, issue, decision or person the other thread is about, in its own words; two threads that merely share a word are not connected, and the answer must not have said they were |
| "The later thread changes the earlier information" rests on observed timestamps | for the rows that establish which thread is later, `internal_date` is non-null and `internal_date_provenance` is `gmail_internal_date`; the ordering the answer states matches those values; and the answer describes them as when Gmail received the message, not as when it was sent or written |
| A change is a change | the later thread's cited row states something that contradicts, supersedes or narrows a specific statement in the earlier thread's cited row; "adds detail" is not "changes the earlier information" unless the answer says exactly that |
| "Do not invent a connection" was honoured | if no pair of threads passes the second row, the answer said so rather than presenting one |

**Chronology, both questions.** Where the answer orders messages, the order must come from
`internal_date` and the answer must not have derived it from message ids, positions in a
list, or the order the rows arrived in. The first run of Question 4 ordered by identifier
because the rows carried no timestamps; the rows now carry them with provenance, so an
answer that still orders by identifier is a finding about the client, and one that orders by
`internal_date` while calling it "sent at" is a finding about the answer's precision.

**Which half the client reads.** Run 2 showed that "the rows carry them" was true of the
structured half only: the text mirror, which is what the Desktop surface reads, carried no
attribution and no timestamp on any row until 2026-09-22. It now carries both, with their
provenance, on every row (`attribution <provenance>: address <a>, stated_addresses <n>`, a
fenced `display_name` line when the header had one, `internal_date <stamp> (<provenance>)`),
under a one-sentence note that says what they are not. The chronology check therefore reads
the same on either half; on a run before that date it can only be applied to the structured
results, and an answer that had only the text in front of it could not have passed it.

### The verdict per question

- **Resolved** - every row in its table is yes, and the answer's own separation of
  explicit statements from inference matches what the checks found.
- **Partially resolved** - the decision, or the connection, is supported by cited rows, but
  at least one reason, rejected alternative, or the chronology claim is not in the results
  or was stated as fact where the results make it inference.
- **Insufficient evidence** - the cited rows do not support the central claim (the decision
  for Q2, the connection for Q4), or the citations are not in the results, or the answer
  itself declared the evidence insufficient and the results agree.

Write the verdict with the rows that decided it. A verdict is not a score, and two verdicts
are not a trend.

## Run 1, 2026-09-22: failed, preserved, and what it left open

The first run under these instructions failed and is preserved privately as run 1. Its
diagnostics were off - the variable was set in a shell and not in the Desktop config, which
is why step 3 above now shows the config - and its server log carried repeated
`ValueError: do_handshake_on_connect should not be specified for non-blocking sockets` from
the TLS handshake. Mechanism: the socket clamp handed a handshake a timeout of `0.0` once the
allowance was spent; a zero socket timeout is non-blocking mode, not "fire at once", and the
`ValueError` it provokes is mapped by nothing and left the client as an internal error
instead of a `budget_exhausted` decline. Fixed by refusing the operation with the transport's
own typed timeout before the socket is touched (`net/deadline.py::allowance`), held by
regressions on the real `httpcore` stream at every boundary.

**The timings, recorded and not attributed.** Calls 7, 8, 10 and 13 of run 1 ran about 104,
110, 110 and 110 seconds from request to error, each with the traceback inside the retrieval
ladder's `list_messages`. Nothing in this document says where those seconds went. Two source
findings made while reading for run 1 are fixed (the adapter's own Gmail requests ran under
no deadline; the socket clamp was scoped per client rather than per request - see
`EXPLORATORY_RUNS_2026-09-21.md`), and neither is offered as the cause.

## Run 2: one diagnostics-enabled run, not the retest

One question, one fresh chat, the setup above with step 3 confirmed by the banner before the
question is sent. Ten-minute ceiling; do not name a tool; copy every tool result block whole.
Its purpose is the diagnostics file, and what it must yield is, for every call:

- the start line's `queued_ms` - time behind the call lock, invisible to `elapsed_ms`;
- the end line's `elapsed_ms`, `allowance_ms`, `deadlines`, `overrun_ms`;
- the socket figures `sockets`, `connect_ms`, `tls_ms`, `write_ms`, `read_ms`, and
  `cold_load_ms` where the first semantic query paid it.

Read it with `python tools/dev/check_calls.py calls.jsonl --tolerance-ms 750` and keep the
output. A call the client saw take a minute is then one of: a large `queued_ms` (it waited
for another call), a large `deadlines` count with `allowance_ms` to match (it was several
bounded retrievals in sequence), a large `connect_ms` (name resolution or the network path),
a large `read_ms` over few sockets (Gmail answering slowly), or an `overrun_ms` past the
tolerance (the deadline not holding, which is a defect). Part two's answer review is not
run on run 2 unless the file is clean; the questions and the mailbox are unchanged either way.

## What this cannot show

That the product navigates better than before. That either question would resolve for a
different owner, a different mailbox, or the same owner on a different day. It shows that
four mechanisms behave on the shipped process the way the suite says they do, and it puts
the two answers against the evidence the client was given - which is what the first five
runs could not do, because that evidence was not kept.
